# Решения

Коротко: что решили и почему. Отсюда берём аргументы для презентации.

## Архитектура

**Одно SPA на все роли, PWA вместо нативного приложения.** Одна кодовая база для телефона рабочего, телефона мастера и десктопной панели; установка на главный экран без магазина приложений; обновления приходят сами. Android обязателен по ТЗ — PWA на Chrome закрывает его полностью, iOS работает через Safari.

**Статус наряда меняется только в `state_machine.py`.** Таблица переходов — данные, а не разбросанные if-ы. Из неё же строятся кнопки следующего действия и подсказки в ошибках («Сейчас доступно: «Принять в работу», «Поставить в очередь»»). Тест сверяет таблицу со спецификацией: лишний переход не проскочит.

**Живые события публикуются только после commit.** Изменение и событие о нём не расходятся: клиент не увидит статус, который откатился.

**PostgreSQL LISTEN/NOTIFY вместо Redis.** Бэкенд, бот и планировщик — разные процессы, а WebSocket-соединения живут в бэкенде. NOTIFY доставляет события между процессами без ещё одного сервиса в docker-compose. Предел полезной нагрузки 8 КБ нам не мешает: событие несёт id и статус, данные клиент перезапрашивает.

**Переносимые типы в БД.** Перечисления хранятся как VARCHAR, время — всегда в UTC с часовым поясом (свой тип `UTCDateTime`). Поэтому тесты и локальный запуск без Docker идут на SQLite, а прод и CI — на PostgreSQL 16, на одной и той же схеме.

**`external_id` во всех справочниках.** Ключ для будущей синхронизации с 1С / ERP / ТОиР; REST API с OpenAPI (`/api/docs`) — готовая точка интеграции.

## Безопасность

**Вход: логин + 4-значный ПИН, JWT на 12 часов (смена с запасом).** ПИН хранится как PBKDF2-SHA256 с солью. Четыре цифры легко перебрать, поэтому после 5 неверных попыток вход по этому логину блокируется на 5 минут. Счётчик в памяти процесса — для одного экземпляра бэкенда этого достаточно; при горизонтальном масштабировании перенесём его в БД.

**Роль проверяется дважды:** на фронте (какие экраны показывать) и на бэке (`require_role`). Руководитель видит всё, но не меняет статусы нарядов.

## Данные

**Присутствие на смене — поле `on_shift`.** В проде заполняется из табеля или СКУД, в прототипе — сидом и мастером. Отсюда статус «не на смене».
