## 1. Продукт в одном абзаце

Мастер смены выдаёт наряд с телефона за ≤6 нажатий. Исполнитель получает уведомление в Telegram (с кнопками «Принять» / «В очередь» прямо в сообщении) и в PWA, ведёт наряд по статусам, закрывает его с работами, шифром, материалами и фото «после». ИИ следит за сроками, проверяет закрытый наряд (правила + LLM + сравнение фото), выставляет оценку и пишет отчёты, считает рейтинг, находит аномалии в истории за 3 месяца. Финальное слово всегда за мастером.

Роли: `master` (мастер смены), `worker` (исполнитель), `boss` (руководитель), `admin`.

## 2. Стек (не менять без обсуждения)

**Backend:** Python 3.12, FastAPI, SQLAlchemy 2 (async) + asyncpg, Alembic, Pydantic v2, PostgreSQL 16, APScheduler (фоновые задачи), aiogram 3 (Telegram-бот), Pillow + imagehash + piexif (фото), pandas (аналитика), openpyxl (Excel), WeasyPrint (PDF через HTML-шаблоны Jinja2), Anthropic Python SDK (LLM).

**Frontend:** React + Vite + TypeScript (strict), Tailwind CSS, vite-plugin-pwa (Workbox), TanStack Query, React Router, Zustand (минимально), i18next (ru + kk), Recharts, browser-image-compression, шрифты через @fontsource (самохостинг, работает офлайн).

**Инфра:** docker-compose (db, backend, frontend, bot, scheduler), Caddy с автоматическим HTTPS для деплоя, GitHub Actions (линт + тесты).

Одно SPA с маршрутами по ролям: `/w/*` — исполнитель (мобайл), `/m/*` — мастер с телефона, `/panel/*` — веб-панель мастера, `/boss/*` — руководитель, `/admin/*` — справочники. Каждая роль видит только своё (проверка и на фронте, и на бэке).

## 4. Машина статусов (единственный источник правды — `state_machine.py`)

| Код | Название в UI | Кто переводит дальше |
|---|---|---|
| `ISSUED` | Выдан | исполнитель |
| `QUEUED` | В очереди | исполнитель |
| `ACCEPTED` | Принят в работу | исполнитель |
| `REJECTED` | Отклонён | мастер (переназначает) |
| `IN_PROGRESS` | В работе | исполнитель |
| `PAUSED` | Приостановлен | исполнитель |
| `DONE` | Исполнено | система (сразу запускает проверку) |
| `AI_REVIEW` | Проверка ИИ | система → мастер |
| `REWORK` | На доработку | исполнитель |
| `CLOSED` | Закрыт | — (терминальный) |
| `CANCELLED` | Отменён (служебный) | — (терминальный) |

Разрешённые переходы:
- `ISSUED → ACCEPTED | QUEUED | REJECTED(причина обязательна)`
- `QUEUED → ACCEPTED`
- `ACCEPTED → IN_PROGRESS`
- `IN_PROGRESS → PAUSED(причина обязательна) | DONE(форма закрытия обязательна)`
- `PAUSED → IN_PROGRESS`
- `DONE → AI_REVIEW` (автоматически)
- `AI_REVIEW → CLOSED` (мастер подтверждает) `| REWORK` (вердикт ИИ «требует доработки» или решение мастера)
- `REWORK → IN_PROGRESS`
- `REJECTED → ISSUED` (мастер переназначил исполнителя)
- любой нетерминальный → `CANCELLED` (мастер, причина обязательна)
- мастер в любой момент до `DONE` может сменить приоритет и исполнителя — это события, а не статусы.

Каждый переход пишет `order_events` (кто, действие, из→в, время, комментарий, причина) и рассылает событие по WebSocket. Недопустимый переход → HTTP 409 с понятным текстом на русском. Тесты покрывают все разрешённые и несколько запрещённых переходов.

Статус исполнителя вычисляется: `не на смене` (серый) / `свободен` (зелёный) / `в работе` (жёлтый, с номером наряда) / `есть очередь` (синий, с числом N).

## 6. ИИ-модули — как именно делаем

Общий принцип: **детерминированные правила находят факты, LLM объясняет и оценивает смысл.** Так результат воспроизводим, быстрый и не галлюцинирует цифры.

**LLM-шлюз (`services/llm/`).** Все вызовы только через него. Перед отправкой обезличивает: ФИО → «Исполнитель #id», никаких телефонов и ПИН. Модели из env: `LLM_MODEL` (по умолчанию `claude-sonnet-5-5`, для проверки и фото), `LLM_FAST_MODEL` (по умолчанию `claude-haiku-4-5-20251001`, для коротких текстов). Ответы — строго JSON по Pydantic-схеме, с одним повтором при невалидном JSON. Логирует каждый вызов в `llm_calls`. **Если `ANTHROPIC_API_KEY` не задан — включается mock-режим** на правилах и шаблонных текстах: жюри должно суметь запустить репозиторий без ключа и увидеть работающую систему.

**6.1 Контроль сроков** — задача планировщика раз в 30 секунд:
- за `REMIND_BEFORE_MIN` (по умолчанию 30) до срока — напоминание исполнителю;
- просрочка — сообщение исполнителю и мастеру в формате из ТЗ: «Наряд №147 просрочен на 45 мин. Дробилка КМД-1750, участок дробления. Исполнитель: Ахметов Е. Статус: в работе с 09:20. Последний комментарий: “ждём подшипник со склада”» (в Telegram ФИО можно — это внутренний канал, не LLM);
- не принят за 10 мин (аварийный — за 3 мин) — эскалация мастеру с предложением свободного исполнителя той же специальности и кнопкой «Переназначить»;
- повтор каждые `REPEAT_MIN`; просрочка > 2 ч — уведомление руководителю;
- аварийный наряд в Telegram повторяется каждую минуту, пока не принят.

**6.2 Проверка закрытого наряда** (`verification/`), результат за ≤15 секунд, прогресс видно в UI:
1. `rules.py` — полнота (работы, шифр, материалы или явная отметка «без материалов», фото «после» обязательно для внеплановых); время факт/норматив/срок; материалы против нормы по шифру (>1.5× — замечание, >2.5× — доработка).
2. `llm_check.py` — соответствие выполненных работ описанию проблемы и шифру; релевантность материалов типу работ; итог 0–1 и короткое обоснование.
3. `photos.py` — фото «после» существует, EXIF-время внутри окна выполнения, pHash не совпадает с прошлыми фото в базе (дубликат = доработка); если есть фото «до» — мультимодальная модель сравнивает: то ли оборудование, устранена ли видимая проблема, аккуратность (мусор, незакреплённые элементы, нет кожуха); балл 1–5 + confidence.
4. `aggregate.py` — итоговый балл 0–100 и вердикт: `accepted` / `accepted_with_remarks` / `rework`. Любая критическая проблема → `rework`. Confidence < 0.6 → флаг «нужна проверка мастером», ИИ не выносит вердикт сам.

Каждое замечание — конкретное и проверяемое: «Списано 6 л масла И-40А при норме 1,5 л для шифра Г-02» вместо «материалы завышены».

**6.3 Отчёты по наряду.** Исполнителю — балл, что хорошо, что улучшить, время против норматива (уважительный тон, на «вы»). Мастеру — всё: хронология, работы, материалы, фото до/после со слайдером сравнения, вердикт с разбором по каждой проверке, простой. Мастер может согласиться или изменить оценку с комментарием — это сохраняется и учитывается в рейтинге.

**6.4 Аналитика и аномалии** (`analytics/`): детекторы на pandas — топ проблемного оборудования и участков по числу внеплановых и простою; повтор одного шифра на одном оборудовании; поломки ≤7 дней после ППР (с разрезом по бригаде); связь со сменой и временем суток; связь с исполнителем (повторные отказы ≤7 дней); перерасход материалов (z-score по норме); тренд роста внеплановых → прогноз риска отказа. Детекторы возвращают факты с цифрами; LLM превращает их в выводы простым языком + рекомендацию (как в примере ТЗ про конвейер К-3). Мастер может спросить свободным текстом («покажи проблемы участка дробления за месяц») — LLM выбирает детекторы и период через tool use / JSON-план, отвечает с цифрами.

**6.5 Рейтинг** — формула, понятная рабочим (веса в конфиге, обоснование в `docs/DECISIONS.md`):
- 35% — средняя оценка качества (ИИ, с учётом правок мастера);
- 25% — доля нарядов в срок;
- 20% — отсутствие возвратов на доработку и повторных поломок ≤7 дней;
- 15% — объём с учётом сложности (критичность оборудования × норматив);
- 5% — отсутствие отказов без уважительной причины.
Минимум 5 нарядов за период, иначе «недостаточно данных». ИИ пишет каждому короткое пояснение: из чего сложился рейтинг и что поднимет его сильнее всего.

**6.6 ИИ-подбор исполнителя** при выдаче: свободен → нужная специальность → лучший рейтинг по этому типу оборудования → меньше очередь. Показывается первым в списке с меткой и одной строкой «почему».

**6.7 Ассистент мастера (бонус):** чат «Кто свободен из электриков?», «Что просрочено?», «Отчёт за неделю по обогащению» — LLM с инструментами поверх нашего API.

## 7. Тестовые данные (`backend/seed/`)

Детерминированный генератор (`seed=42`), одна команда `make seed`. Минимум из ТЗ: 4 участка (Дробление, Обогащение, Конвейерный транспорт, Ремонтно-механический цех), 25 единиц оборудования (в т.ч. Дробилка КМД-1750, Конвейер К-3, Насос гидравлический Н-7), 2 мастера, 15 исполнителей в 3 бригадах (слесари-ремонтники, электромонтёры, сварщики, смешанно), 20 шифров (М-01…М-06, Э-01…Э-05, Г-01…Г-03, П-01…П-03, С-01…С-03), 40 материалов с единицами, нормативы, 500+ нарядов за 3 месяца с реалистичным распределением, событиями, оценками и простоями. Плюс руководитель и админ.

**Заложенные закономерности (ИИ обязан найти все — это проверяется тестом):**
1. Конвейер К-3: внеплановых поломок в 3× больше среднего, большинство за последние 30 дней — М-02 (подшипник).
2. Один исполнитель: ~30% его нарядов возвращаются на доработку или повторная поломка ≤7 дней.
3. Дробилка КМД-1750: внеплановые поломки в течение 5 дней после ППР, выполненного бригадой №2.
4. Участок обогащения: электрические отказы (Э-*) в ночную смену в 2.5× чаще, чем днём.
5. Один исполнитель систематически списывает смазочные материалы в 2–3× выше нормы.

Также сид для демо: смена «сейчас», 2 свободных слесаря, 1 электрик в работе, 1 с очередью, несколько нарядов в разных статусах.

## 8. Дизайн — главное визуальное отличие

Перед первым экраном создай `docs/DESIGN.md` (токены, типографика, компоненты) и страницу `/dev/ui` со всеми компонентами во всех состояниях. Все экраны собираются только из этих компонентов.

**Идея:** интерфейс как промышленная маркировка на производстве — бирки, таблички оборудования, сигнальная разметка. Он должен выглядеть так, будто сделан для горно-обогатительного комбината, а не как очередной SaaS-шаблон.

**Одна запоминающаяся вещь — карточка наряда в виде бирки-допуска:** слева вертикальная полоса цвета приоритета (у аварийного — сигнальная диагональная штриховка жёлто-чёрная или красно-белая), номер наряда и инвентарный номер оборудования набраны как штампованная табличка (узкий шрифт, крупно, табличные цифры), справа статус. Всё остальное — спокойное и дисциплинированное.

**Палитра:**
- `steel` `#1F2A33` — основной текст и тёмные поверхности;
- `mineral` `#E8EAE7` — фон приложения (холодный серый камень, хорошо читается на солнце);
- `km-blue` `#0B3F8C` — основной акцент, фирменный синий заказчика из логотипа «Костанайские Минералы»;
- `signal-yellow` `#F2C200` — «в работе», сигнальная разметка;
- `signal-red` `#D7261E` — аварийный, просрочка, «требует доработки»;
- `ok-green` `#2E8B3E` — «свободен», «принято»;
- синий статуса «есть очередь» — светлее фирменного, серый «не на смене» — `#8A9299`.
Цвета статусов из ТЗ (зелёный/жёлтый/синий/серый) нигде не меняют смысл. Цвет никогда не единственный носитель смысла — всегда есть текст или иконка. Контраст текста ≥ 4.5:1.

**Шрифты:** IBM Plex Sans (интерфейс) + IBM Plex Sans Condensed (номера нарядов, инвентарные номера, крупные цифры счётчиков), табличные цифры (`font-variant-numeric: tabular-nums`). Проверь, что казахские буквы ә ғ қ ң ө ұ ү һ і отображаются.

**Для работы в перчатках:** зоны нажатия ≥ 56 px на экранах исполнителя (основная кнопка действия — 64 px, во всю ширину, внизу экрана в зоне большого пальца); отступ между опасными кнопками ≥ 16 px; «Отклонить» и «Отменить» — с подтверждением удержанием (hold-to-confirm 800 мс), а не мелким диалогом; вибрация `navigator.vibrate` на подтверждения и аварийные; аварийный наряд — полноэкранное красное уведомление со звуком, которое нельзя смахнуть без ответа. Шрифт основного текста на телефоне ≥ 17 px.

**Тексты интерфейса:** простые глаголы, как говорят на производстве: «Принять в работу», «Поставить в очередь», «Начать», «Приостановить», «Исполнено». Кнопка и результат называются одинаково. Ошибки объясняют, что случилось и что делать, без извинений. Пустые экраны подсказывают действие («Нарядов нет. Новые придут сюда и в Telegram»).

**Не делать (признаки шаблонного ИИ-дизайна):** фиолетовые/градиентные акценты, одинаковые скруглённые карточки с одинаковой серой тенью везде, надписи капслоком над каждым заголовком, стрелки «→» в тексте кнопок, декоративные анимации появления каждого блока, эмодзи в интерфейсе, «стеклянные» полупрозрачные панели. Анимация — только как ответ на действие (смена статуса, раскрытие).

**Панель мастера (десктоп):** слева колонка людей смены с цветными статусами, по центру канбан по статусам, сверху счётчики смены (выдано / выполнено / просрочено / оборудование в простое) крупными цифрами. Новые и изменённые карточки кратко подсвечиваются — видно, что пришло в реальном времени.

Поддержи тёмную тему (полезно в ночную смену) через те же токены.

После каждого крупного экрана делай скриншоты (Playwright, мобильный 390×844 и десктоп 1440×900) в `docs/screenshots/`, смотри на них критически и исправляй: выравнивания, переполнение текста на длинных русских словах, контраст, состояния загрузки и пустоты.

## 9. Нефункциональные требования

- Статусы обновляются у всех за ≤ 5 секунд (WebSocket, автоподключение после обрыва, при переподключении — перезапрос данных).
- Фото сжимаются на клиенте до 1600 px / JPEG 0.8 перед загрузкой, до 5 фото; загрузка ≤ 10 с на мобильной сети; превью на сервере.
- Офлайн (желательно): действия исполнителя складываются в очередь IndexedDB и отправляются при появлении сети; в UI видно «ожидает отправки».
- Вход: логин + 4-значный ПИН, JWT; ограничение попыток.
- Интерфейс полностью на русском, казахский — переключателем (i18next, все строки через ключи с первого дня).
- REST API документирован в OpenAPI (`/docs`) — задел для интеграции с 1С / ТОиР.
- Персональные данные не уходят в LLM (см. шлюз).

## 10. Демо-режим (критично для победы)

`DEMO_MODE=true` включает:
- `POST /api/demo/reset` — пересоздаёт демо-смену за 2 секунды;
- скрытую страницу `/demo` («пульт оператора»): сбросить сцену, «промотать» время у выбранного наряда до просрочки, отправить тестовое уведомление, показать QR-коды для входа на телефонах под разными ролями;
- короткие сроки (минуты вместо часов) для нарядов демо-сцены.
Весь сценарий из раздела 11 ТЗ (9 шагов) должен проходить без ручных манипуляций с базой. Он же — e2e-тест Playwright.
